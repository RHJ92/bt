# notice — 가맹점 안내문 작성 작업 거점

프랜차이즈 가맹점에 나가는 **본부 공지 안내문**(공급가 조정 / 배송 휴무 / 주문처 전환 등)을 노션에 초안으로 작성하는 작업 공간.

**이 파일 하나로 안내문을 처음부터 끝까지 쓸 수 있게 정리돼 있다.** 스킬(`/notice-draft`)은 실행 절차만 담고 판단 기준은 전부 여기에 있으니, 작업 전 이 파일을 먼저 읽는다.

- `notice/` 폴더에는 과거 발행 원본(.hwp)이 톤 참고용으로 보관돼 있다
- 사용자 요청 예: **"이 내용(표/이미지) 안내문 양식에 맞춰서 옥된장·석문어 나눠서 작성해줘"**

## 0. 작성 전 점검 — 여기서 걸러야 할 실수들

지금까지 실제로 났거나 날 뻔한 실수다. 초안을 쓰기 전에 훑는다.

| # | 점검 항목 | 틀리면 생기는 일 |
|---|---|---|
| 1 | **하단 법인명을 브랜드에 맞췄나** | 전부 옥된장으로 통일했다가 교정받은 적 있음 |
| 2 | **단가가 판매가(가맹점 공급가)인가** | 매입가(jt)를 쓰면 원가가 점주에게 노출된다 |
| 3 | **적용일을 넘겨짚지 않았나** | 요청 표의 `요청일`과 `적용일`은 다른 열이다. 적용일 열이 비어 있으면 묻거나, 쓰고 나서 확인 요청 |
| 4 | **점주가 기한 안에 할 일이 있나** | 있으면 콜아웃을 맨 위로 (§4-1). 중간에 뒀다가 점주가 사전 발주를 놓친 사고가 있었다 |
| 5 | **금액이 들어가는 표에 부가세 라벨을 붙였나** | §4-2 |
| 6 | **같은 시기·같은 품목 건이 이미 있나** | 있으면 합친다. 두 장으로 나가면 날짜가 충돌하는 것처럼 읽힌다 (§4-3) |
| 7 | **출고일과 매장 입고일을 구분했나** | "출고 재개 8/26"만 쓰면 점주는 8/26에 받는 줄 안다 (§4-4) |
| 8 | **동일 단가 변종을 한 줄로 합쳤나** | §5-① |
| 9 | **배경이 2줄을 넘지 않나** | 길면 사용자가 직접 잘라낸다. 과정 설명은 내부 문서용 |

## 2. 브랜드 규칙 (★ 가장 중요)

한 건의 조정·공지라도 **브랜드별로 나눠서 각각 발행**한다. 요청 표의 브랜드 열이 `옥된장/석문어`처럼 공용이면 해당 품목을 **양쪽 안내문 모두에** 넣는다.

| 브랜드 | 인사말 머리 | 하단 법인명 |
|---|---|---|
| 옥된장 | `옥된장F&B 본부에서 …` | **옥된장에프엔비** |
| 석문어 | `석문어F&B 본부에서 …` | **석문어에프엔비** |
| 정백선 | `정백선F&B 본부에서 …` | **정백선에프엔비** |

- 공통 주소: **경기도 성남시 수정구 위례광장로 19, 12층 1202호** + `[법인명]`
- ⚠️ 과거에 하단 법인을 전부 옥된장으로 통일했다가 교정받음 → **법인명은 반드시 브랜드에 맞춰 교체**
- **브랜드마다 달라지는 것** — 인사말 브랜드명 / 하단 법인명 / 품목표 내용 / (품목 구성이 다르면) `목적` 문구의 방향
  - 예: 옥된장은 인상·인하 혼재라 "조정(인상·인하)", 정백선은 인하만이라 "인하". **인하만 받는 점주에게 "인상·인하"라고 쓰면 없는 인상을 걱정하게 된다**
- 나머지 본문·맺음말·주소는 전 브랜드 동일

## 4. 유형 무관 절대 규칙

### 4-1. 점주 액션이 필요하면 콜아웃을 맨 위로 ★

기한 안에 점주가 **직접 뭘 해야 하는** 건(사전 재고 확보, 선마감 발주 등)은 노란 콜아웃을 **`-아래-` 직후, `계획` 블록보다 위**에 둔다.

- **왜** — 일회용품 주문처 통합 안내(8/25 개시)에서 사전 재고 확보 콜아웃을 전환 일정표 뒤에 뒀더니 일부 점주가 사전 발주를 놓쳤다. 콜아웃이 있었는데도 표를 읽는 동안 지나쳐 버렸다
- **본문은 근거, 콜아웃은 지시다.** 지시가 근거보다 뒤에 오면 안 읽힌다
- 콜아웃에 세 가지를 반드시 넣는다 — **① 언제까지 ② 무엇을 ③ 안 하면 어떻게 되는지**
- 제목은 **기한 + 동작** (`**8/20(목)까지 사전 발주 필수**`). "안내드립니다"류는 쓰지 않는다
- **액션이 없는 단순 고지(공급가 조정 등)에는 넣지 않는다.** 매번 붙으면 강조가 죽는다

```
<callout icon="⭐" color="yellow_bg">
	**8/20(목)까지 사전 발주 필수**                                  ← ① 기한
	- 8/22(토) \~ 8/26(수)는 매장 입고가 불가합니다.                  ← ③ 안 하면
	- 8/20(목)까지 **약 1주일 사용량**을 미리 발주해 주세요.           ← ② 할 일
	- 8/20(목) 발주분은 8/21(금) 입고되며, 다음 입고는 8/27(목)입니다.
</callout>
```

### 4-2. 금액이 들어가는 표에는 부가세 라벨

표 **라벨 옆**에 괄호로, 연회색으로 붙인다. 표 아래 `※` 줄이 아니다.

```
- 상품 안내 <span color="gray">(과세 품목 부가세 별도)</span>
```

- **위치가 라벨 옆인 이유** — 표기 기준은 숫자를 읽기 전에 알아야 쓸모가 있다. 표가 둘 이상인 안내문에서 어느 표에 걸리는 기준인지도 분명해진다
- **고정이다.** 표에 면세 품목만 있어도 빼지 않는다. 과세·면세 구분은 표의 `과세여부` 열이 품목별로 담당하고, 이 괄호는 "표에 적힌 숫자는 부가세를 포함하지 않은 값"이라는 단가 기준 표기다. 서로 다른 정보라 충돌이 아니다
- 문구는 `(과세 품목 부가세 별도)`로 확정. `(공급가 부가세 별도)` → `(표기 단가는 부가세 미포함)`을 거쳐 정착했으니 **다시 뒤집지 말 것**
- `※` 줄과 역할이 갈린다 — **`※`는 점주가 할 행동**(몰에서 확인 등), **라벨 괄호는 표 읽는 기준**

### 4-3. 한 사건은 한 장으로

주문처 변경과 물류·배송 변경처럼 **같은 시기에 같은 품목에 걸리는 건**은 나눠 쓰지 않는다. 점주가 두 장을 받으면 별개 사건으로 읽고 날짜가 충돌하는 것처럼 보인다. (실제로 별건 3부를 썼다가 합친 사례가 있다)

### 4-4. 출고 기준과 매장 입고 기준을 구분

`8/25 몰 개시·주문 → 8/26 출고 → 8/27 매장 입고`처럼 하루씩 밀린다. "8/26 출고 재개"만 쓰면 점주는 8/26에 받는 줄 안다.

- 일정표에 **매장 입고일 행을 따로** 둔다
- 콜아웃에도 **다음 입고일을 못박는다**

### 4-5. 배경은 최대 2줄

조정 사유 한 줄 + 필요 시 한 줄 더. **매입 구조·협상 과정 같은 내부 논리는 빼고 결론만.** 과정 설명은 내부 문서용이다. (3문장으로 썼다가 사용자가 한 문단을 통째로 잘라낸 적 있음)

## 5. 유형별 포인트

### ① 공급가 조정 안내

표 6열: `상품명 / 과세여부 / 단위 / 기존 단가 / 변경 단가 / 증감율`

- **단가는 판매가(=가맹점 공급가) 기준.** 매입가(jt 매입가)는 어디에도 노출하지 않는다
- 요청 표의 증감율도 **판매가 기준**으로 계산돼 온다. 받은 값을 그대로 쓰되 검산은 판매가로 한다
- 증감율은 부호와 방향 표시 — **인상 = 빨강(red), 인하 = 파랑(blue)**. 예: `+5.45% (인상)`, `-3.10% (인하)`
- **상품명은 매장용 대표명으로 간소화** — 내부코드(ODJ/SM)·규격·원산지·변종기호를 뗀다
  - `소꼬리절단S(ODJ/10kg)_BOX_(소고기 : 호주산)` → **`소꼬리절단`**
  - 규격이 필요하면 `단위` 열로 옮긴다 (`BOX (3kg×4ea)`)
  - `(계근)` 같은 표기는 단위 열의 `KG`와 중복이라 뺀다
- **동일 단가 변종은 한 줄로 합친다** — S·M·Y, H·S 등 단가가 같으면 한 행. 단가가 다르면 행을 분리한다
  - 실적: 7품목 → 4행 / 12품목 → 8행(옥된장 4·석문어 3·정백선 1)
- 배경은 §6의 고정 문안을 쓴다

### ② 배송 휴무 안내 (가락시장 하계휴무 등)

내용 3단: **① 일반 농산품(휴무·재개 일정) → ② 배송일정표 → ③ 주문 불가리스트**

- 배송일정표: 첨부 이미지를 노션 표로 재현. 날짜(요일) 헤더 / ●·X / 제주도 행 `yellow_bg` / X·특이사항 red
- 노션 표는 셀 병합 불가 → 세로 병합 항목은 첫 열에 풀어서 표기하고, 필요하면 UI에서 병합하라고 안내한다
- **D-2 선마감 발주**처럼 놓치기 쉬운 액션은 콜아웃으로, **위치는 맨 위**(§4-1)

### ③ 주문처 전환(발주처 통합) 안내

내용 3단: **① 전환 일정표 → ② 통합 대상 품목 리스트 → ③ 주문 방법**

- 전환 일정표 2열(`일자 / 내용`). 마지막 주문일·입고 불가 기간은 red + 볼드
- 마지막 주문 관련 액션은 콜아웃으로, **위치는 맨 위**(§4-1) — 일정표 뒤에 뒀다가 점주가 놓친 사례가 있다
- 품목 리스트 4열(`No / 상품명 / 규격·용량 / 박스 입수`)
  - **No는 엑셀 상품번호가 아니라 1부터 매기는 일련번호** — 마지막 숫자가 곧 품목 수가 되게 한다
  - **배송이 바뀌는 품목만이 아니라 그 브랜드에 세팅된 전품목**을 싣는다
- **가격 열은 넣지 않는다** — 전환 안내는 주문 경로 공지지 단가 공지가 아니다. 대신 표 아래에 `※ 품목별 가맹점 공급가는 (주문처)에서 확인해 주시기 바랍니다.` 한 줄
- 상품명은 `[브랜드]` 접두·내부 표기를 떼고 대표명만. 전용 품목만 브랜드명을 앞에 붙여 구분(`옥된장 전용 냅킨`)
- 견적서의 `_택배` 표기는 떼고 쓴다 — 포장보스 통합 품목은 전 품목 택배 운영이라 구분할 이유가 없다

### ④ 스펙 변경 안내 (생산 공장·정형 규격 변경)

같은 부위인데 **생산 공장이 바뀌어 정형 규격이 달라진** 경우. 점주가 매장에서 "평소와 모양이 다르다"고 느껴 클레임으로 번지지 않게 하는 게 목적이다.

내용 3단: **① 사용 부위 안내 → ② 기존 스펙과의 차이 → ③ 본사 사전 테스트 결과**

- **부위 설명을 반드시 넣는다.** 점주는 부위명은 알아도 해부학적 위치까지는 모른다. 어디에 붙은 무슨 부위인지, 현장 용어(마구리 등)가 어느 경계를 가리키는지 한 줄씩 풀어 쓴다
- 차이는 **비교표 3열**(`구분 / 기존 스펙 / 변경 스펙`)로. 정형 범위 · 형태 · 살량·풍미 순
- 사진이 있으면 **좌·중·우 어느 것이 무엇인지** 본문에서 짚어준다. 사진만 붙이면 점주가 뭐를 봐야 할지 모른다
- **③는 반드시 넣는다** — "본사가 미리 확인했고 정상 공급품"이라는 문장이 이 안내문의 핵심이다. 살량·맛에 차이가 없다는 점을 명시한다
- **대상 상품을 상품코드로 특정한다.** 점주는 발주 화면에서 코드로 구분하므로, `구분 / 상품코드 / 상품명 / 스펙` 4열 표를 앞쪽(①)에 둔다. 여기서는 **상품명을 발주 화면 표기 그대로** 쓴다 — §5-①의 대표명 간소화 규칙을 적용하지 않는다. 간소화하면 점주가 발주 화면에서 못 찾는다
- 편차가 언제까지 갈지 **기간을 명시한다** (`CC311992 출고분부터 올해 남은 기간 동안`). 기간이 없으면 점주는 영구 변경으로 받아들인다
- 점주 액션이 없으므로 §4-1 콜아웃은 넣지 않는다
- ⚠️ **공급처가 준 원인 설명을 그대로 옮기기 전에, 그 설명이 확정된 것인지 확인한다.** BBQ M 건에서 수입사가 처음 "부위 특성에 따른 정상적인 편차"라고 안내해 그대로 초안을 썼는데, 패커 재확인 후 **"작업이 불균일해 제거 대상 끝단(조각 BBQ)이 일부 포함된 것"**으로 정정됐다. 발행 전이라 고쳤지, 나갔으면 두 번 공지해야 했다. **수입사·생산자 확인이 끝났는지 묻고 나서 발행한다**
- 원인이 "정상 스펙 차이"가 아니라 **일시적 품질 편차**로 밝혀지면 비교표를 `구분 / 내용` 4행(**현상 · 원인 · 품질 영향 · 향후**)으로 바꾼다. R vs M 같은 스펙 대조표는 전제가 틀려진다
- 편차를 숨기지 않되 **"품질 영향 없음"을 바로 뒤에 붙인다.** 사실만 적고 끝내면 감액 요구로 번진다
- 부위 설명 전에 **축종(소/돼지)을 확정**한다. 백립은 소·돼지 모두 있어 설명이 갈린다
- **일시적 편차라면 "한시적"임을 세 박자로 못박는다** — ① 왜 한시적인가(겹친 요인을 나열) ② 지금 어떻게 되고 있나(현지 안정화 진행) ③ 앞으로는 어떤가(국내 입고분도 점차 안정). "일시적 편차입니다" 한 마디로는 약하다. 점주의 진짜 걱정은 "앞으로도 계속 이러냐"이고, 거기에 답해야 한다
  - 요인은 **겹쳤다는 사실**까지 적는다 (`가공장 폐쇄 + 기존 공장 가동 중단 + 인력 수급 문제가 동시에`). 단일 원인으로 쓰면 "관리 부실"로 읽히고, 겹친 상황으로 쓰면 불가항력으로 읽힌다
  - 다만 근로자 이탈 규모 같은 **공급처 내부 사정은 쓰지 않는다.** 요인 이름까지만
  - 향후 전망은 `~될 예정` / `~로 보고 있습니다`로 완화한다. 시점을 적으면 약속이 된다 (BBQ 건에서 수입사가 "연내 예상"이라 했지만 확답이 아니어서 안내문에 시점을 넣지 않았다)

## 6. 고정 문안 (그대로 복붙)

### 배경 — 공급가 조정

```
- 축산품 공급가는 산지 및 국내 시장 시세에 따라 변동될 수 있습니다.
- 이에 따라 아래와 같이 해당 품목의 공급가를 조정하였습니다.      ← 인하만이면 "인하하였습니다"
```

품목군이 다르면 **한 줄씩 나눠 쓴다** (`- **축산품** : …` / `- **곰피** : …`).

| 품목군 | 고정 멘트 |
|---|---|
| 축산품 | `공급가는 산지 및 국내 시장 시세에 따라 변동될 수 있습니다.` |
| 곰피(해조류) | `공급가는 원물 수급 여건에 따라 변동될 수 있습니다.` |

**이번 조정의 원인을 설명하지 말고 상시 조건을 고지한다.** `변동될 수 있습니다`가 핵심 — 사실 주장이 아니라 조건 고지라 따질 대상이 없고, 매번 반복돼도 자연스럽다. 반복 노출될수록 "축산물은 원래 등락한다"를 점주가 당연하게 받아들인다.

- 반대로 `~때문에 올랐습니다/내렸습니다`는 쓰지 않는다. 인상·인하가 섞인 안내문에서 **"같은 환율인데 왜 어떤 건 오르고 어떤 건 내리냐"**는 반문이 바로 나온다
- `목적`에서도 원인 특정을 뺀다 — `원물 시세 변동에 따른 … 공급가 조정/인하`. "수입 돈육 시세 하락분 반영" 같은 표현은 그 주장이 맞는지 따질 수 있게 만든다
- 억지로 한 문장에 묶으면 "축산 원물과 해조류 원물의 산지 시세"처럼 없는 설명을 만들게 된다

### 맺음말

```
앞으로도 본사는 원가 변동 상황을 지속적으로 확인하며, 가맹점의 운영 부담을 줄이고 안정적인 물류 공급이 이루어질 수 있도록 최선을 다하겠습니다.
**문의사항은 담당 슈퍼바이저(SV)에게 문의하여 주시기 바랍니다.**
```

물류·배송 건이면 첫 줄을 `본사는 물류 상황을 지속적으로 확인하며, 가맹점의 운영에 불편이 없도록`으로 바꾼다.

## 7. 노션 작성 시 주의

- **한국어는 유니코드 이스케이프 대신 직접 기입한다.** 이스케이프로 넣다가 `곧`을 `곷`으로, `겉절이`를 `갉절이`로 잘못 쓴 사고가 두 번 있었다. 넣은 뒤 반환된 마크다운에서 오타를 눈으로 확인할 것
- 상품명 속 `*`(예: `5kg*2pk`)는 `\*`로 이스케이프한다.
- ⚠️ **언더스코어 `_`는 안전하지 않다.** `_BOX_` 같은 표기는 `update_content`를 한 번 더 돌리는 순간 **손대지 않은 자리에서도 이탤릭으로 재파싱되어 언더스코어가 사라진다** (2026-09-09, 상품명 셀에서 발생). `update_content`는 페이지 전체를 마크다운으로 다시 직렬화하기 때문이다.
  - 상품코드·상품명처럼 **원문 그대로 남아야 하는 값**은 마크다운을 거치지 말고 **REST API로 rich_text를 직접 써넣는다** — `PATCH /v1/blocks/{block_id}` 에 `{"table_row":{"cells":[[{"type":"text","text":{"content":"..."}}], ...]}}`
  - 같은 이유로, 마크다운 편집 후에는 **언더스코어가 살아 있는지 반드시 되읽어 확인**한다
- 표는 rich text만 — 셀 안 볼드는 `**…**`, 색은 `<span color="red">…</span>`
- 연회색 **글자색**은 `<span color="gray">…</span>` — 계획 헤더의 회색 **배경** `{color="gray_bg"}`와는 다른 속성이다
- 빈 줄은 `<empty-block/>`
- `update_content`로 **같은 줄에 걸치는 편집 두 건을 한 번에** 보내면 뒤 편집이 앞 편집 결과를 못 찾아 내용이 날아갈 수 있다. 한 건씩 나눠 보내고 결과를 확인한다
- 페이지 생성 시 `__unparsedToolInput` 래핑을 쓰지 않는다(파싱 에러)
- **이미지 첨부는 MCP로 안 된다. 노션 REST API 파일 업로드를 직접 쓴다** (2026-09-09 확인). 토큰은 환경변수 `NOTION_API_TOKEN`. 3단계다.
  1. `POST /v1/file_uploads` (json: `filename`, `content_type`) → `id`, `upload_url` 수신
  2. `POST {upload_url}` 에 multipart `files={"file": (name, bytes, "image/jpeg")}` → status `uploaded`
  3. `PATCH /v1/blocks/{page_id}/children` 에 `{"type":"image","image":{"type":"file_upload","file_upload":{"id":fid}}}` + `"after": <캡션 블록 id>` 로 원하는 위치에 삽입
  - 헤더는 `Authorization: Bearer`, `Notion-Version: 2022-06-28`. 2단계에서는 Content-Type을 직접 넣지 않는다
  - **원본은 리사이즈해서 올린다** — 장변 1600px·품질 85면 3\~4MB 사진이 300\~460KB가 된다. 점주는 휴대폰으로 열기 때문에 원본 그대로면 로딩이 답답하다
  - ⚠️ 이미지를 넣은 뒤에는 **`replace_content`를 쓰면 안 된다.** 이미지 블록이 통째로 날아간다. 이후 수정은 반드시 `update_content`(부분 치환)로 한다
