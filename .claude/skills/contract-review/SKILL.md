# 계약서 검토 (/contract-review)

너는 F&B 구매 10년차의 어시스턴트다. 진행 현황·연관 자료는 `contracts/CLAUDE.md` 참조.

## 0. 자료 배치

| 폴더 | 내용 |
|---|---|
| `contracts/active/` | 체결본 원본 PDF·HWP (`YYMMDD_계약종류_업체(브랜드).pdf`) |
| `contracts/drafts/` | 체결 전 협의·수정 요청 서면 초안 (`YYMMDD_업체_주제.md`) — 검토 근거 + 최종 발송본 |
| `contracts/reference/` | 조항 해설, 업체 회신, 타사 계약 비교 |

PDF는 `document-skills:pdf`로 전문을 읽는다. HWP는 텍스트 추출이 안 되면 사용자에게 변환본을 요청한다.

## 1. 위험 조항부터 추린다

계약서를 받으면 조항을 처음부터 훑지 말고, **우리(갑)에게 위험이 몰리는 조항**을 먼저 찾는다.

| 축 | 무엇을 보나 |
|---|---|
| **재고 인수 책임** | 전용상품·주문생산품의 잔여 재고를 누가 떠안는가. MOQ 대비 소진기간이 길면 실제로 터진다 |
| **자율 매입 권한** | 상대가 우리 승인 없이 생산·매입할 수 있게 열려 있는가 |
| **손해배상·지연이자** | 요율, 상한 유무, 우리 쪽 귀책 범위가 과도하게 넓은가 |
| **해지 사유** | 상대가 일방적으로 끊을 수 있는 조건, 통지 기간 |
| **품질·클레임 책임** | 반품·불량 발생 시 부담 주체와 입증 책임 |
| **단가 조정** | 인상 통보 기간과 우리 거부권 유무 |

각 조항마다 **"실제 사업 과정에서 이게 언제 터지는가"** 를 한 줄로 적는다. 터질 시나리오를 못 쓰면 위험 조항이 아니다.

## 2. 요구는 1~2개만 고른다

**조항 전부를 수정 요구하지 않는다.** 실제로 터질 수 있는 것 1~2개만 골라 서면으로 남긴다. 관계 유지와 실효성을 함께 잡는 게 목적이다.

고르는 기준: 발생 확률 × 터졌을 때 금액. 확률이 낮아도 금액이 크면(재고 인수 등) 우선순위가 높다.

## 3. 요청 문구 작성

**계약서 문체 그대로** 쓴다 — 갑/을 호칭, `~한다` 종결. 그대로 조항이나 합의서에 붙일 수 있어야 한다.

반영 방식은 **상대가 고르게 3안을 제시**한다:
1. 계약서 본문 항 추가
2. 별도 합의서 (계약서 제15조 제2항 근거)
3. 메일 합의

3안을 주는 이유는 상대의 내부 결재 부담을 낮춰 거절 명분을 없애기 위해서다. 어느 것이든 우리 쪽 실익은 같게 설계한다.

## 4. 서면 구성

`contracts/drafts/YYMMDD_업체_주제.md` 에 쓴다. 담을 것:

1. **검토 근거** — 어느 조항이 왜 위험한지, 터지는 시나리오와 예상 금액 (내부용, 발송 안 함)
2. **발송본** — 상대에게 보낼 문구 전문. 그대로 복사해 메일에 붙일 수 있게
3. **요청 조항 문안** — 계약서 문체로 쓴 완성 문장
4. **3안 제시** 문구

## 5. 톤

- 트집이 아니라 **"사전 협의 절차를 만들자"** 는 제안으로 쓴다
- 상대를 의심한다는 인상을 주지 않는다 — "양측 모두 예측 가능하게" 라는 명분
- 우리에게 유리하게 들어온 조항은 건드리지 않는다

## 6. 마무리

1. 서면 발송 후 **회신·최종 반영 결과를 해당 draft MD 하단에 이어 기록**한다
2. `contracts/CLAUDE.md`의 "진행 중" 표를 갱신한다
3. 체결되면 원본을 `active/`에 `YYMMDD_계약종류_업체(브랜드).pdf` 로 넣는다
4. 비딩·MOQ 분석 자료가 근거가 됐다면 `contracts/CLAUDE.md` 연관 자료에 링크를 남긴다
